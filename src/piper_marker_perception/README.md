# piper_marker_perception

识别 ArUco 标定板，解出板子位姿，再换算成规划层要的按压目标。

**当前状态：离线部分已完成并通过验证；ROS 节点还没写。**
见 `piper_elevator_manipulation/docs/marker_perception_plan.md`。

### 快速跑起来

```bash
# 相机是独占的，先把 cam_view.py 关掉
python3 scripts/marker_locator.py \
    --ros-args --params-file config/marker_locator_orbbec.yaml
```

它会打印板子位姿，并把**画了检测框的实时画面**发到
`/perception/debug_image/compressed`：

```bash
ros2 run rqt_image_view rqt_image_view /perception/debug_image/compressed
```

默认发在**相机光学系**（`wrist_depth_camera_optical_frame`）—— 不需要机械臂、
不需要 TF、不需要手眼标定，插上相机就能跑。

要用机械臂系下的位姿，加上 `-p target_frame:=base_link`，那就需要
`robot_state_publisher` + `/joint_states` + 写进 URDF 的手眼标定，
**而且只有在机械臂停稳时才发**（相机在腕部，运动中时间误差会直接变成位置误差）。

## 快速开始（现在就能做，不需要相机/机械臂）

### 1. 生成板子并打印

```bash
cd /ws/src/Piper_ros/src/piper_marker_perception
python3 scripts/make_board.py --out ~/aruco_board.png
```

打印时设 **100% / 实际大小**，不要「适应页面」。

印完做两件事：

1. **量图下方的刻度线** —— 应该是 100.0 mm。不是就说明打印缩放不对。
2. **拿卡尺量一个 marker 的边长**，填回 `config/board.yaml` 的 `marker_length`；
   同样量一下 marker 之间的**空隙**填 `marker_separation`。

> ⚠️ 这两步不能省。家用打印机有 ±1% 缩放，110 mm 的板子可能差 1 mm，
> 而 1% 的尺度误差会原样变成 1% 的位置误差 —— 在 0.4 m 处就是 4 mm。

### 2. 先跑自测确认代码没问题

```bash
python3 scripts/selftest_offline.py
```

会在合成图上验证板系约定和位姿恢复精度（不需要相机）。

### 3. 拿手机/相机拍几张板子，跑离线检测

```bash
python3 scripts/detect_board.py ~/photos \
    --camera-info /path/to/camera_info.yaml \
    --out ~/photos_debug
```

输出每张图的 marker 数、重投影 RMS、距离、平移量；`--out` 里的调试图画了
角点、ID 和板系坐标轴（红 +X / 绿 +Y / 蓝 +Z，蓝轴应指向相机）。

**调检测参数就用这个**：拍十来张真实距离和角度的照片，一次跑完，
看什么条件下 marker 数和重投影误差开始变差 —— 比移动机械臂快得多也稳定得多。

## 板子 → 按键：那个固定的位姿关系

板子不是要按的东西，它是**能看到的东西**。整条链路靠一个物理前提：

> **板子和按键刚性固定在同一块面板上。**

在这个前提下，按键的位置和朝向由板子的位姿经过一个**常量变换**得到：

$$
T_{base \leftarrow 按键} = T_{base \leftarrow 板子} \cdot \underbrace{T_{板子 \leftarrow 按键}}_{\text{常量，装好后不变}}
$$

这个常量在 `board.yaml` 里分成**两块**存（因为实际就是这么量出来的）：

| 字段 | 含义 | 谁能量 |
|---|---|---|
| `tip_in_board` | 杆尖**应该落到的点**，板系，米 | 卷尺能估，教示更准 |
| `press_axis_in_board` | 按压方向（指向按键内部），板系单位向量 | **只有教示能量** |

默认按压轴是 `(0, 0, -1)` = 板系 −Z。板子和按键共面时这就是对的（两者法线相同）。
只有按键行程轴和面板法线不一致时才需要改 —— 那种按键**斜着按会卡死**，
所以方向是真的输入，不是形式。

### 教示（推荐，比卷尺准一个量级）

```bash
# 需要感知节点在跑且此刻能看到板子
ros2 run piper_marker_perception teach_press_offset.py --name red --poses 3
```

手动把杆尖**顶到按键中心**，回车。脚本记录那一刻：

```
T_base←板子      来自感知节点
T_base←press_tcp 来自 TF（杆尖真实位置）
```

于是

$$
tip_{板系} = R_{base \leftarrow 板子}^{\mathsf{T}} \cdot (p_{tcp} - t_{base \leftarrow 板子})
$$

而**按压轴是免费的**：杆尖顶在按键上时，工具的 +Z **就是**操作者用小臂瞄的方向，
取同一个变换就得到它在板系下的表示。

`--poses 3` 让它在 3 个不同臂位姿各测一次。那个偏移是个**常量**，三次结果必须一致 ——
不一致说明问题不在教示，而在**手眼标定**（那是三次之间唯一变化的东西）。
这把标定质量变成现场可读的数。

输出是一段 YAML，**手动贴回** `config/board.yaml`。脚本不直接改文件，因为那会
把解释这些数字含义的注释一起冲掉，而那些注释是文件价值的大部分。

### 桥节点

```bash
ros2 run piper_marker_perception press_target_bridge.py --ros-args -p target:=red
```

> ⚠️ ROS 参数**必须**跟在 `--ros-args` 后面。否则 rclpy 会把 `target:=red`
> 当成 remap 规则，参数根本没传进去，然后报"缺少 target 参数"，非常费解。

会用到的参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `target` | — | **必填**，按键名 |
| `config` | 包内 `board.yaml` | 配置路径 |
| `board_topic` | `/perception/board_pose` | 输入 |
| `topic` | `/press/target_pose` | 输出 |
| `publish_rate_hz` | 5.0 | 持续发布（契约允许持续发）|
| `max_age_s` | 1.0 | 板子位姿超过这个年龄就停发 |
| `require_taught` | true | `taught: false` 时拒绝发布 |
| `direction_sign` | 1.0 | 和规划层同名参数，给存了外法线的人 |

它会拒掉三类输入，**每类只在状态变化时报一次**（不然 5 Hz 会刷屏）：

| 拒绝什么 | 为什么 |
|---|---|
| `taught: false` | 配置里是占位值，拿它去按压 = 按到不知道哪里 |
| 板子位姿在相机系 | 规划层只认 `world` / `base_link`，相机系会被它静默拒收 |
| 目标在工作空间盒外 | 提前用和规划层**同一组边界**拦下，报错清楚得多 |
| 板子位姿超过 `max_age_s` | 停止发布，避免拿旧位姿指挥 |

## 板系约定（钉死在代码里）

```
原点 = 板子几何中心
+X  向右（面向板子看）
+Y  向上
+Z  垂直板面向外，指向观察者
```

⇒ **按压方向 = 板系 −Z**。

`solvePnP` 给出的位姿是 `T_camera_optical <- board`，用的就是这个坐标系。
打印出来的板子贴在面板上、正面朝机械臂时，蓝轴（板系 +Z）应指向相机。

## ⚠️ 两条必须遵守的事

⚠️ 这里**已经没有图像旋转这回事**。相机以前是倒装的，那 180° 被故意留着、
由手眼标定吸收 —— 那套约定**已废弃**：相机已经物理翻转，原始图本来就是正的。
以后如果又有相机被倒装，**把它物理翻过来**，不要在这里重新引入旋转 ——
绕光轴的 180° 是个*固定*旋转，它会无声地折进板子位姿里，而且错的答案
看着最顺眼。

### 1. 板子贴反了不会被发现 —— 只有 marker 数量能抓

这是实测出来的，不是推测：

| 情况 | marker 数 | 重投影 RMS | 解出的位姿 |
|---|---|---|---|
| 正常正对 | 9/9 | 0.21 px | 正确 |
| **贴反** | **1/9** | **0.14 px** | **看起来完全正常，但错** |

原因：从背面看，每个 marker 都是镜像的，而镜像的 ArUco 图案不是合法编码，
所以 8 个直接解不出来。但**剩下的 1 个足够 `solvePnP` 拟合出一个朝前、
指向正确、重投影误差很低的位姿** —— 而且是错的。

**⇒ `min_markers` 必须设成接近板子上 marker 的总数**（本板子 9 个，建议 ≥ 4，
严格一点用 ≥ 6）。这是唯一可靠的信号。

默认 `min_markers: 0` 表示**跟随 `board.yaml`**：门槛自动取 marker 总数的 60%
向上取整（3×3 → 6，单个 → 1）。所以换板子形态只改 `board.yaml` 一个文件，
不用再记着 `marker_locator_orbbec.yaml` 里还有个数要一起改 —— 两处不一致时的
表现是"永远说没拍到"，而不是报错。

## 配置

### `config/board.yaml`

```yaml
board:
  dictionary: DICT_4X4_50     # 容器里 25 种字典都可用
  markers_x: 3
  markers_y: 3
  marker_length: 0.030        # ★ 实测值，米
  marker_separation: 0.010    # ★ 实测值（两个 marker 之间的空隙）
  first_marker_id: 0
  accepted_ids: [0,1,2,3,4,5,6,7,8]
```

板子总尺寸 = `3×30 + 2×10 = 110 × 110 mm`。

### 检测器参数

在 `aruco_board.py` 的 `DETECTOR_DEFAULTS` 里，可以按需覆盖：

```python
detector = spec.make_detector(cornerRefinementWinSize=7, adaptiveThreshConstant=5.0)
```

`cornerRefinementMethod = CORNER_REFINE_SUBPIX` **不要关** —— 它是精度影响
最大的一个参数，关掉之后位姿噪声大约差一个数量级。

## 换相机：只改配置，不改代码

相机的**全部差异**都在参数文件里，现成的一份：

| 文件 | 相机 |
|---|---|
| `config/marker_locator_orbbec.yaml` | Orbbec DaBai DCW2（腕部相机）|

```bash
ros2 run piper_marker_perception marker_locator.py \
    --ros-args --params-file <包>/config/marker_locator_orbbec.yaml
```

换相机时只改三处：

| 参数 | 当前值 |
|---|---|
| `device_hint` | `orbbec,dabai,sonix` |
| `width` / `height` | 640×480 |
| `camera_info` | `camera_info_orbbec_640x480.yaml` |

⚠️ **`device_hint` 是必须的**。早期版本把 `"orbbec"` 写死在代码里，结果一个
完全正常的罗技摄像头永远找不到 —— 它的名字是 `UVC Camera (046d:0825)`。

⚠️ **别为某只相机在代码里开分支。** 中间临时挂过一只桌面测试用的 Logitech
C270，代码里因此长出了分辨率和内参的分支；相机换回 Orbbec 之后那一整条路
都删掉了，只留下下面两节的实测数据 —— 它们是**规则**的证据，规则对现在这只
相机一样成立。所以后面提到 C270 的地方都是历史，照着去找 C270 的参数文件
是没有的。

### ⚠️ 同一个相机的不同分辨率，可能是不同视场

这是实测撞出来的，不是从手册上抄的。当时那只是桌面测试用的 C270，两种分辨率
下板子都放在卷尺量得的 0.600 m 处：

| 分辨率 | fx 真值 | 水平视场 | 对角视场 | 板子像素宽 | 节点读出 |
|---|---|---|---|---|---|
| 640×480 | 802.9 | 43.5° | 53.0° | 140 px | 0.6003 m |
| 1280×960 | 1399.0 | **49.2°** | **59.5°** | 244 px | 0.6008 m |

两者的焦距比是 **1.743**，不是 2.000。也就是说 640×480 模式用了较小的一块
传感器区域，视场比 1280×960 **窄 12%**。

（注意 1280×960 的对角视场 59.5° 和规格书的 60° 差 0.8% —— 这一点下面还会用到。）

后果：**不能按分辨率比例换算内参**。硬乘 2 得到 1695，距离读出 0.689 m，
偏长 15%。所以每份内参都要写清它是在哪个分辨率上测的，用哪个分辨率就配哪一份。

**现在这只 Orbbec 的情况正好反过来，所以更要小心。** 规格书那 84.3° 是 16:9
的横向视场，而 640×480 是 4:3 —— 只裁掉左右，**纵向视场留下来了**：标称 54.0°，
实测 53.4°（差 1.1%），而横向从 84.3° 掉到 **67.7°**。把 54.0° 按 16:9 推回去
正好得到 84.3°，两个数字确认是同一只镜头。但要是拿 84.3° 当成 640×480 的
横向视场去反推焦距，就会以为差了 **1.35 倍** —— 体检脚本一开始正是这么判的，
把一个正确的标定报成了不合格。

`marker_locator` 仍然会在分辨率不匹配时自动换算（那是个合理的第一猜测），
但**会把上边的反例写在告警里**，提醒你这不是稳妥的做法。

### 分辨率与内参是一对

请求的分辨率不一定拿得到：填 `1920x1080` 而相机只支持到 `1280×960` 时，
OpenCV 会**静默协商降级**，不报错。而内参只在测它的那个分辨率上成立 ——
640×480 的内参配 1280×960 的帧，所有焦距差 1.74 倍，**所有距离就差 1.74 倍**，
而且解出来的位姿看上去完全自洽。

所以 `marker_locator` 会**读回相机实际给的分辨率**：

- 和请求的不一致 → 告警
- 和内参记录的不一致 → 换算 `fx`/`fy`/主点，并告警（带上上面的反例）
- 内参没记录分辨率 → 告警说无法核对

启动时还会打印**视场角**：

```
[INFO] lens 43.5 x 33.3 deg, fx=802.9 fy=802.9
```

视场角是唯一能和物理常识对账的数 —— 网路摄像头上挂个 16° 的镜头一看就不对，
而 `fx=2299` 不查规格书看不出来。

### 配置路径

参数文件里写 `config/camera_info_orbbec_640x480.yaml` 就够了，不用绝对路径。
同一个脚本在源码树里和 `ros2 run` 安装后所处的层级不同，`resolve_config_path`
会依次试：当前目录 → 脚本旁边 → 安装后的 share 目录。

（这个曾经是个真 bug：`DEFAULT_CONFIG` 按 `dirname(dirname(__file__))` 拼，
从源码跑没问题，一 `ros2 run` 就变成 `lib/config/board.yaml`。）

### 两台相机的标定数据不能混用

不是因为旋转差异 —— 那个已经没有了。是因为镜头和分辨率本来就不一样：
同一只相机换个分辨率视场就可能不同（43.5° / 49.2°），何况换型号。
内参和外参都是**每台相机、每个分辨率一份**。

### 偶发的 libjpeg 噪音（无害）

```
Corrupt JPEG data: 3 extraneous bytes before marker 0xd3
```

有些摄像头的 MJPG 帧尾部多塞几个字节，libjpeg 会抱怨但**照常解码**。那只罗技
在 1280×960 下会刷这条，现在的 Orbbec 一次都不出。试过
`cv2.utils.logging.setLogLevel`（OpenCV 4.5.4 没这个属性）和
`OPENCV_LOG_LEVEL` 环境变量（无效）—— 这些消息是 libjpeg 直接写 stderr 的，
没接进 OpenCV 的日志系统。压不掉，忍一下。

## 收到一份内参，先体检，别直接用

```bash
ros2 run piper_marker_perception check_intrinsics.py <内参文件> --lens orbbec
```

只做算术，不碰相机。查的是**重投影误差查不出来的那类错误**：五个畸变系数
加上焦距和主点，自由度比拟合所需的多，所以一个跑偏的求解器能把残差压到
0.1 px，同时让模型在拟合用的那几千个像素之外完全不可用。

同事交来的第一份就是这样一个真实例子（原文件是 `intrinsics.json`）：

| 检查项 | 结果 |
|---|---|
| fx 与 fy | 相差 13.7%（真实传感器是方形像素，正常 <1%）|
| 视场 | 15.8° × 10.3°（那只相机在 640×480 下实测是 43.5° × 33.3°）|
| 径向项抵消 | 画面四角处量级之和 0.1258，合起来只有 −0.0183，抵消掉 6.9 倍 |
| 径向因子 | 出画面 1.72 倍就翻号 —— 会折过光轴，真实镜头不会 |
| **重投影误差** | **0.128 px —— 好看，但它不能说明内参是对的** |

结论：焦距是真实值的 **2.86 倍**，所以**所有距离被放大 2.86 倍**。
实机验证过：板子用卷尺量得在 **0.600 m** 处，节点读出 **1.626 m**，比值 2.86。

### ⚠️ 板子尺寸量错，会把规格书「证明」成错的

这一节是一段真实的踩坑记录，因为它的形状很典型。

C270 规格书写「60° 对角」。我们一开始量出 marker 边长 27 mm，用它反推得
1280×960 的水平视场只有 46.9°（对角 56.9°）—— 于是写下结论：**「规格书是错的」**，
并把按 60° 反推的 1385.6 标成了废弃。

后来改用**长基线量法**（量整个 3×3 阵列的外圈宽，量法见 `config/board.yaml`），
量到 105 mm，反推出 marker 其实是 **28.5 mm** 而不是 27 —— 偏了 5.6%。

把板子尺寸改对之后：

| | 27 mm（错） | 28.5 mm（对） | 规格书 |
|---|---|---|---|
| 1280×960 的 fx | 1477.0 | **1399.0** | 1385.6 |
| 对角视场 | 56.9° | **59.5°** | 60° |

**规格书是对的**，差 0.8%。而卷尺反推（板子 28.5 mm + 距离 0.600 m）和规格书
这两条**完全独立**的路径，在 1280×960 上吻合到 **1%**。

教训有三层：

1. `fx` 和 `marker_length` 在**单次距离测量**里是**退化**的 —— 得到的是一个
   `fx × L` 的乘积，分不开两者。要分开，必须有一个独立的长度基准。
2. **量长基线。** 量 105 mm 读 ±0.5 mm 是 ±0.5%；量单个 28 mm marker 同样
   读 ±0.5 mm 就是 ±1.8%。差 4 倍。
3. ⚠️ **一个错的输入，能让一个正确的外部参考看起来是错的。** 当时如果没有
   规格书这条独立线索，这个错会一直藏着。

这类结果几乎总是一个原因：标定时棋盘姿态不够多样，径向畸变没有被真正观测到，
求解器就把焦距和畸变互相补偿掉了。重标定时图像 ≥15 张、棋盘要倾斜、
要出现在画面四角、要占满画面。

⚠️ 这不是「PnP 坏了」。PnP 会忠实地按你给的内参算 —— 内参错了，它给出的
也是一个自洽的、整体错尺度的位姿。所以**唯一能在现场抓出它的办法是量距离**。

## 手眼标定：相机装在工具上的哪个位置

```bash
ros2 run piper_marker_perception hand_eye.py \
    --session ~/capture/2026-09-30 \
    --camera-info config/camera_info_orbbec.yaml
```

相机固定在工具上、板子固定在桌上，所以每个姿态都满足

```
T_base←end[i] · X · T_cam←board[i] = T_base←board      ← 处处相同
```

右边不变，`X` 就唯一确定。`cv2.calibrateHandEye` 是一次调用的事。

### 但求解器自己的输出不能告诉你它对不对

它返回「最贴合所给数据的 X」，而且**无论数据对错都会返回一个**。
没有残差可读，没有阈值可越。内参错了，它给出一个自洽的错答案，
看上去和正确答案一模一样。

**能告诉你的是上面那个式子本身：板子不动。** 把 X 代回去，每个姿态
都应该对板子的位置得出同一个结论。散了多少，误差就是多少。

```
 ③ 板子在 base_link 下（应该处处相同）
     平均位置  (+0.2800, +0.0200, +0.0300) m
     最大偏离  0.0 mm      [好]
     最大转角  0.00°      [好]
     结论      可信（好）
```

⚠️ **散布小是必要不充分。** 姿态没转动时，**任意** X 都能让所有姿态
精确一致 —— 散布读出完美的 0.000 mm，而解错了 1.6×10⁷ mm。
所以工具把**姿态转动量**当硬门槛：

| 指标 | 含义 | 门槛 |
|---|---|---|
| 姿态跨度 | 姿态之间**最大**相差多少度 | ≥ 15° |
| 转轴分散 | 相对旋转的轴指得多散 | ≥ 15° |

⚠️ 用的是「最大两两相差」而不是「最小」。最小那个在 20 个姿态里必然
很小，会把好数据报成坏数据 —— 这个错犯过一次，自测里现在有断言盯着。

### 合成自测：不用相机、不用机械臂

```bash
ros2 run piper_marker_perception selftest_handeye.py
```

手眼是 `AX = XB`。反过来跑 —— 挑一个 X、挑一个板子位置、挑一组姿态，
正演出「相机应该看到什么」—— 就成了完整的测试数据。相机到了之后，
把合成数据换成 PnP 的真数据，**求解器一行都不用改**。

22 项断言里，值钱的是错误注入那几项：

| 注入 | 结果 |
|---|---|
| 内参错 2.86 倍 | 平移错 **353.6 mm**，自检散布 **217.3 mm** → 抓住 |
| 同上，但看重投影误差 | 只有 **0.98 px** —— 说不出内参是错的 |
| 角点噪声 0.5 px | 平移错 2.8 mm（20 个姿态）|
| 只平移不转动 | 求解器返回 1.6×10⁷ mm 的垃圾，**散布却是 0.000 mm** |

最后一行就是那个陷阱，现在它是一条自动化断言。

### 输出：两个坐标系，别漏了第二个

`calibrateHandEye` 解出的是**光学系**的，URDF 要的是**机械系**的，
两者差 `optical_joint` 那个固定的 90°：

```
T_tool←link = T_tool←optical · T_optical←link
```

漏掉会得到一个看着挺合理、实际全错的外参。工具两个都打印，并给出
一行可以直接粘的 `<origin>`：

```xml
<origin xyz="-0.035000 -0.000000 0.070000"
        rpy="0.000000 -1.570796 0.000000" />
```

这条是可验证的：自测从 `wrist_depth_camera.xacro` 的设计值
（`xyz="-0.035 0 0.07" rpy="0 -1.57079632679 0"`）正演出合成数据，
工具又把它原样还原成上面这行。

⚠️ 而且万向锁（俯仰 ±90°）时角度不唯一，工具会取 `roll=0` 的那个代表 ——
否则会印出 `rpy=(−55.5, −90, +55.5)°` 这种看着就像坏了的东西。

## 为什么不用 `cv2.aruco.GridBoard` 建 objPoints

`GridBoard` 对「板系原点在哪、轴朝哪」有自己的定义，而且**在 OpenCV 版本之间
变过**。`solvePnP` 只能对得起喂给它的点，所以 `aruco_board.py` 里**自己算**
object points。代价是对 marker 间距做点算术，收益是同一个位姿在任何一个
OpenCV 上含义都一样。
